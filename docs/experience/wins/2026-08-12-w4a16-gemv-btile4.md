# W4A16 GEMV BTILE 16→4 — CUDA, 2026-08-12

> Status: Shipped

## Goal

Improve W4A16 decode throughput on V100 (sm_70) for
ThinkingCap-Qwen3.6-27B-W4A16.

## What worked

`W4A16_MARLIN_BTILE` 16→4 in `quantized_gemv_marlin.cu`. The accumulator
array `half2 sum_h2[BTILE]` drops from 32 to 8 registers, raising occupancy.
For B=1 decode the weight-read count is unchanged (one y-block,
`valid_b=1`), so the change is a free occupancy win on the decode path.

Also removed the one-shot `fprintf` grid debug print and its `<cstdio>`
include from the FFI entry point.

## Parameters

- Baseline: BTILE=16, ~20 tok/s (prior session measurement)
- Treatment: BTILE=4, 23.3 tok/s (3 runs, identical)
- Model: ThinkingCap-Qwen3.6-27B-W4A16, V100 32GB, sm_70
- Bench: `bench_decode.py`, 128 tokens, greedy, single stream

## DSpark evaluation (negative result)

Tested `--spec-type dspark --dspark-block-size 11` on top of BTILE=4.
Acceptance rate k≈4.4 tokens/chain (rank probe: draft top-1 is usually
correct), but end-to-end decode is 17.6–21.3 tok/s — below the 23.3 plain
baseline. The verify step runs B=11 through the BTILE=4 kernel, which
launches 3 y-blocks and reads weights 3×. BTILE=16 (single y-block for
B=11) was tested in a prior session and also broke even. The draft + verify
overhead exceeds the acceptance benefit on V100; DSpark is not viable on
this workload.

## Rule

Register-pressure knobs (accumulator array size) are free wins when the
weight-read count is unchanged for the target batch. BTILE should be sized
for the common case (B=1 decode), not the speculative-verify case.
