# v0.2.0 CUDA release unblock — FlashMLA sm_90a-only in T1, custom-AR nccl-gate, DeepGEMM stub syms

## Context

The `v0.2.0` tag (initially at `d8e0a4a2`) failed every CUDA release job —
T1 (sm_80/86/89/90), V100 (sm_70), Blackwell (sm_100/120) all red, only
macOS Metal green, so `Create GitHub Release` was **skipped** (it gates on
`build-macos && build-linux`). No v0.2.0 was ever published. Three distinct
CUDA build blockers, all surfaced only in the release/Docker arch config
(`--features cuda`, no `nccl`, no `deepgemm-native`, per-job
`TORCH_CUDA_ARCH_LIST`) which differs from the pod's proven build
(`cuda,nccl` + `ARLE_CUDA_ENABLE_DEEPGEMM_NATIVE=1`, `TORCH_CUDA_ARCH_LIST=9.0`).

Bench-exempt: build/CI config + a non-native-only NOT_SUPPORTED stub. No
runtime/perf path changes.

## What Worked

Commit `7ffe866a`. Verified green on a throwaway `v0.2.0-rc1` tag before
promoting the public `v0.2.0` (release.yml/docker.yml have no
`workflow_dispatch` — the only trigger is a `v*` tag, so an rc tag is the
license-or-kill lane).

1. **FlashMLA / FA3 → sm_90a-only, decoupled from `TORCH_CUDA_ARCH_LIST`**
   (`crates/cuda-kernels/build.rs`). FlashMLA's sm90 sparse-FP8 kernels use
   thread-block clusters (launch_bounds) + WGMMA that require the `sm_90a`
   arch variant; clusters hard-fail on sm_80/86/89/70
   (`cannot specify max blocks per cluster for this GPU architecture`). The
   per-file nvcc loop was applying the *global* arch list to every `.cu`
   including FlashMLA. Fix: detect FlashMLA/FA3 TUs (path component
   `flashmla` / `flash-attention` + the shim stems) and emit
   **only** `-gencode=arch=compute_90a,code=sm_90a` for them, the global
   `arch_args` for everything else. This is how upstream FlashMLA/FA3 ship —
   sm_90a-only cubins LOAD and RUN on cc-9.0 Hopper (H100/H20). FlashMLA now
   builds **inside the T1 image** and the T1 binary carries FlashMLA-sm_90a
   (dispatched only on sm_90 by `dsv4_flashmla_decode_enabled`, dormant
   elsewhere). **Not** globally disabled. The monolith-era
   `ARLE_CUDA_DISABLE_FLASHMLA=1` was removed from Dockerfile + the T1
   release job (kept on V100/Blackwell where the kernel is dormant anyway).

2. **`custom_all_reduce.cu` gated on `CARGO_FEATURE_NCCL`** (build.rs). Its
   bf16 one-shot path (`upcast<nv_bfloat16,8>` →
   `no suitable conversion from "nv_bfloat16" to "half"`) only instantiates
   through `CustomAllreduce::allreduce`, which is nccl-gated everywhere on the
   Rust side (`tp.rs mod oneshot` = `#[cfg(all(cuda, nccl))]`). On a non-nccl
   build the `extern "C"` decls in `ffi/comm.rs` emit no relocations if never
   called, so dropping the `.cu` from the compile list is safe. This was the
   V100 + T1 non-nccl link blocker.

3. **DeepGEMM stub-symbol parity** (`csrc/gemm/deepgemm_bridge_stub.cu`).
   `dsv4_deepgemm_fp8_gemm_nt_cuda` and
   `dsv4_deepgemm_fp8_paged_mqa_logits_fused_cache_cuda` were defined in
   `deepgemm_native.cu` (under `#ifdef ARLE_ENABLE_DEEPGEMM_NATIVE`) and
   referenced by Rust FFI, but had **no** `#ifndef`-side NOT_SUPPORTED
   fallback → `rust-lld: undefined symbol` on every non-native build (T1,
   Docker). Added both stubs; audited all 9 native vs 9 stub symbols — now
   identical.

Result on `v0.2.0-rc1` (and `v0.2.0`): T1 CUDA ✅, macOS Metal ✅, Blackwell
✅, Docker ✅. `Create GitHub Release` published macOS + T1 + Blackwell
binaries + `install.sh` + `SHA256SUMS.txt`.

## V100 sm_70 — TileLang bf16 wall (deferred in v0.2.0, wired in v0.2.1)

After the three fixes, V100 nvcc native `.cu` compilation **passes** (the
errors above are gone). It then fails further along, at **TileLang AOT
codegen**: `Layout infer conflict between p and p_bf16 in T.Parallel loop`
(LayoutInference pass, tilelang 0.1.11). Volta sm_70 has **no native bf16
tensor cores** (bf16 arrived with Ampere sm_80); the
[sm-coverage policy](../../plans/sm-coverage.md) bf16→fp16 fragment lowering
isn't reconciling for the attention P@V cast under the pinned tilelang.

**v0.2.1 resolution — wire the existing sm_70 patch into the V100 CI job.**
The fix already exists: `scripts/sm70_tilelang.patch` adds a `cuda.fma`
(Volta scalar-FMA) GEMM fallback for the dtype/layout combos sm_70 MMA can't
serve (upstream PR [tile-ai/tilelang#2339](https://github.com/tile-ai/tilelang/pull/2339),
unmerged → no wheel carries it). The patch is **C++** (`src/cuda/op/gemm.cc`,
compiled into `libtilelang.so`), so the pinned wheel can't carry it — the
`build-linux-v100` job now **builds TileLang from source** with the patch
applied (`scripts/patch_tilelang_sm70.sh`), `--no-build-isolation` so the C++
build sees the already-pinned cu12 torch / apache-tvm-ffi stack, **non-editable
`pip install`** so the result reproduces the official wheel's data layout
(`src/tl_templates` + `3rdparty/cutlass/include`) that build.rs's
`tilelang_include_dirs` probe requires.

Why this is **zero-blast-radius** on the just-green T1 build:
- The V100 job is **SM-pinned** (`TORCH_CUDA_ARCH_LIST='7.0'`) on its **own
  runner** with its **own Python env**. The from-source patched TileLang
  replaces the wheel **only in that job** — T1 (sm_80/86/89/90) + Blackwell
  keep the pinned `tilelang==0.1.11` wheel untouched. No pin-to-pod violation
  (the pod is sm_90, uses the wheel).
- The patch applies **clean** to a fresh `v0.1.11` checkout (verified
  `git apply --check`).

**Compile-green is the only CI-verifiable bar; runtime stays best-effort.**
No V100 hardware exists in CI or on the pod (sm_90 H20), so the sm_70 binary's
needle-gate correctness is the **V100-host-owner's** responsibility per
sm-coverage.md — this change makes the binary *exist*, not *proven-on-Volta*.
The job stays `continue-on-error` / non-gating: a green compile attaches the
artifact, a failure is fix-forward and never nukes the release.

## Rule

- **A binary you can't validate is not "fixed" — but you can still ship the
  *artifact* on a non-gating best-effort lane.** sm_70 green-compile without
  V100 hardware is not a proven-on-Volta claim; keep the job
  `continue-on-error`/non-gating and pin runtime correctness on the host-owner.
  "Can't run the needle gate" defers the *correctness verdict*, not the
  *compile*.
- **An SM-pinned CI job is a blast-radius firewall — exploit it.** A from-source
  patched toolchain (here: TileLang + the unmerged `cuda.fma` PR) is safe to
  drop into a single SM-pinned job because its runner + Python env are isolated;
  the default-tier (T1) wheel pin is untouched, so "bump risks T1" and
  "pin-to-pod" both dissolve. Build **non-editable** + `--no-build-isolation` so
  the result matches the official wheel layout the consumer's probe expects and
  the C++ build sees the already-pinned deps.
- **Release/CI arch config is a distinct build surface from the pod's.**
  `--features cuda` (no nccl/deepgemm-native) + per-job `TORCH_CUDA_ARCH_LIST`
  exercises link paths the pod's `cuda,nccl,deepgemm-native` build never
  hits — verify the release config, not just the pod config.
- **Sm-specific kernels compile sm-specifically.** FlashMLA/FA3 are
  sm_90a-only; never let the global `TORCH_CUDA_ARCH_LIST` leak into their
  nvcc gencode, and never blanket-disable them — the T1 binary carries them,
  the runtime gate keeps them dormant off-Hopper.
- **`#ifdef`/`#ifndef` symbol pairs must define the same symbol set** or the
  non-native build dies at link, invisibly, only in the config that omits the
  native feature.
- **No `workflow_dispatch` → verify on a throwaway `vX.Y.Z-rcN` tag** before
  promoting the public tag; tag dereference + create-release behave
  identically, so rc green ⇒ public-tag green.
