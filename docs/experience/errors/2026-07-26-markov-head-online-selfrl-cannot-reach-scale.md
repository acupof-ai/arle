# The online markov-head sidecar cannot reach training scale — and the markov path taxes 22.5%

## Context

The rank probe said the DSpark draft ranks the trunk's token 2nd 50% of the
time, and DSpark's markov head is exactly the mechanism for that defect: the
draft block is one non-causal forward, so row r's logits cannot condition on the
token actually chosen at row r-1, and `bias = w2·w1[prev]` injects precisely
that conditioning. Our Qwen3.6-27B-DFlash checkpoint ships neither head (58
tensors: body + fc + norms only), and the cold-start path already materializes a
trainable one with `w2 = 0`.

So the experiment was free of new code: run the existing sidecar on the same
data DeepSpec uses, install the head, measure.

Dataset copied from DeepSpec's recipe (`scripts/data/README.md`):
`mlabonne/open-perfectblend`, held-out user turns, answers generated by the
target model itself — their offline regeneration step run live instead of cached.
4000 train / 200 eval prompts, `max_tokens` 256, greedy, block 16, c=8, 1×H20.

## Root Cause

Two independent walls, both measured.

**1. Sample scale.** 1500 prompts of traffic produced **220 sidecar steps at
batch 8 = 1760 experiences**, against a head of 2 × 248320 × 256 = **127M
parameters**. DeepSpec's config runs global batch 512 on 8 GPUs against a 38 TB
target cache and trains the whole draft body. We are ~64× below their
per-step sample count on a CPU autograd trainer.

The consequence is quantifiable, not a hunch. Sampling 32 previous tokens from
the saved head and forming `bias = w2·w1[prev]`:

| trained bias | value |
|---|---:|
| std | 0.00089 |
| p99 | 0.00427 |
| within-row spread (max−min) | **0.052 logit** |

`w2` is 100% nonzero — the gradient did flow everywhere — but reordering rank 2
above rank 1 means crossing the top-2 logit gap, which is O(1) on a converged
LM. The learned bias is one to three orders of magnitude short of entering the
competition.

**2. The markov path costs 22.5% throughput.** Turning the head on leaves the
batched-argmax path (`block_argmax` is gated on `markov.is_none()`) and pays a
`[248320, 256]` gemm plus a row memcpy and an add **per block row per slot** —
re-serializing exactly what the batched-argmax and ragged-window tranches
removed earlier the same day.

| arm | k_mean | aggregate tok/s |
|---|---:|---:|
| baseline, no markov | 3.831 | **203.8** |
| trained head (220 steps) | 3.837 | 158.0 (**−22.5%**) |
| during training (head + sidecar) | — | 140.9 |

k_mean 3.831 → 3.837 is noise; the head is neither helping nor hurting
acceptance. The 22.5% is a clean reading of the markov path's own cost (`w2`
nonzero, no sidecar running).

## Fix

Order was wrong. Batch the markov path first — one
`[248320, 256] × [256, B·block]` gemm per tick in place of `B·block` row gemms,
the same shape as the ragged-window draft attention — so the tax approaches
zero. Only then is a serious training run worth its cost, and that run needs the
offline lane: target cache, CE 0.1 + hidden-L1 0.9, lr 6e-4, global batch 512,
on a GPU trainer rather than CPU autograd.

Two artifacts kept: the head at `markov_head.safetensors` (254 MB, the draft
loader's own tensor names) and the eval/train prompt splits on the pod host
share.

## Rule

Before training a head, price the path that runs it. A head that must earn back
22.5% before its first useful token is not a training problem yet — it is a
kernel problem. And check the learned parameter's *magnitude* against the
quantity it must overcome: `w2` was 100% nonzero, which reads as "training
worked" and means nothing when the resulting bias is 0.05 logits against an
O(1) gap. Nonzero is not the same as in-scale.
